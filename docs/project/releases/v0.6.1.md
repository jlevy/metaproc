# Metaproc v0.6.1

A patch release for the Metabrowser plugin, whose views have been wrong since v0.4.0
against the Metabrowser the `browser` extra pins.

Nothing in the engine, the CLI, or the cloud path changed.
What changed is what a run looks like when you open it in the browser: a runpool’s
Charts tab drew its summary and then said charts were unavailable, the Stats tab could
not find the run behind a nested runpool log, a process graph’s hover card never
appeared and raised an error on every mouse move across a node, and a process graph kept
its light palette under the dark theme.
All four are fixed.

No public CLI surface, process-file field, runtime artifact shape, plugin entry point,
or adapter default changed, and the `browser` extra pins the same Metabrowser it pinned
in v0.6.0.

## What’s Changed

### Fixes

- **Runpool charts draw on first open.** Since v0.4.0 the Charts view never requested
  the host’s on-demand `chart` bundle, so unless another view had already loaded
  Chart.js the run summary appeared over the host’s “Charts are unavailable” notice.
  Opening the tab after any view that had pulled the bundle in worked, which is why the
  tab looked intermittent rather than broken.
  The view now requests the bundle alongside its data, so the two arrive together.

- **The Stats view finds the run behind a nested runpool log.** Since v0.4.0 it took the
  run directory from `.logs/<file>` only, so `.logs/runpool/events.jsonl` and step or
  worker logs asked the server for stats on the log path and failed.
  The run directory is now everything before `.logs/`, whatever sits below it.

- **A process graph’s hover card sits under its node.** Since v0.4.0 the plugin passed
  the pointer event where the host’s tooltip takes the anchor element, so the card was
  never placed, and each mouse move over a node raised an error calling a `move()` the
  host does not have. The card now anchors to the node it describes and is positioned
  once, which is also what keeps it still while the pointer travels across the node.

- **Process graphs read in the dark theme.** The host supplies dark values only for its
  text, surface, and border tokens, so since v0.4.0 step, dependency, and file cards,
  chips, edges, and error panels kept light pastels under light text.
  The plugin now defines their dark values: kind accents and neutral roles alias the
  host’s dark surfaces and borders, and hued roles keep their hue at dark lightness.

### Documentation

- The [plugin README’s](../../../src/metaproc/metabrowser_plugin/README.md) validation
  commands now run. It printed `metab plugins show` and `metab plugins doctor`, which the
  pinned Metabrowser does not provide; the commands it prints are now
  `metab --plugin metaproc --json` and `metab --doctor`.
- “Metabrowser” is spelled one way across the shipped help topics, the plugin README,
  and the changelog. The mixed-case form appeared in 49 places; no package, module,
  command, or environment-variable name changed.
- The [cloud-dispatch runbook](../../../src/metaproc/docs/cloud-dispatch.runbook.md)
  describes a `gcp run` job’s console destination generically: the console is a file on
  the job’s run-storage mount, and the storage product is only what a deployment mounts
  as that storage. The `METAPROC_GCP_FILESTORE_*` variables, the `gcp filestore` command,
  the `--no-filestore` flag, and the `filestore_*` config fields keep their names, since
  they are what an operator sets and types.

## Compatibility

- **Metabrowser 0.12 is not yet supported.** The plugin targets browser plugin SDK 0.5,
  which `metabrowser==0.9.1` provides; 0.12 provides SDK 0.7 and refuses a manifest
  declaring any other SDK. Under a separately installed 0.12 the plugin’s views do not
  load and its files fall back to the generic Markdown, JSON, and JSONL views —
  unchanged from v0.6.0. Install with `uv tool install 'metaproc[browser]'` to get the
  matched pair.

- **Three transitive lock moves clear published advisories.** The lock moves `pyasn1` to
  0.6.5 and `opentelemetry-api` to 1.45.2 to clear published advisories, and `certifi`
  to 2026.10.23, which removes two emSign roots and adds none.
  All three reach an installed Metaproc only through the `gcp` extras — `pyasn1` under
  `google-auth`, `opentelemetry-api` under `google-cloud-logging`, `certifi` under
  `requests` — and none is a declared Metaproc dependency, so the requirements an
  install resolves are unchanged.

- **Nothing public changed.** No CLI command or flag, no process-file field, no runtime
  artifact shape, no plugin entry point, and no adapter default (`opus`, `gpt-5.5`,
  `gemini-3.1-pro-preview-customtools`, `sonnet`) was changed, removed, or renamed.
  No dependency floor moved.

- **Still open from v0.5.0: the GCP image interpreter.** Metaproc has required Python
  3.14 since v0.5.0, and container bootstrap refuses the shipped wheel on an image whose
  `/opt/venv` is older.
  That image build lives outside this repository and is still unverified (`mp-mo74`).
  Until it is confirmed or rebuilt on 3.14 and re-pinned, dispatch with `--no-wheel` or
  from 0.4.x; `metaproc help cloud-dispatch` says the same.

- **Still open from v0.4.0: Gemini and ignored files.** Gemini steps ship with
  `context.fileFiltering.respectGitIgnore: False`, so a Gemini step’s file tools can
  read ignored files anywhere in the workspace, `.env` included.
  Whether the default should become opt-in is still open as `mp-x1qh`; treat a workspace
  a Gemini step runs in as readable by that step.
