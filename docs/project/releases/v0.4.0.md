# Metaproc v0.4.0

A `mode: composite` step can now declare `for_each`, so a process runs a whole child
process per item rather than a single step per item.
Underneath that, local execution collapsed onto one shared thing: one execution context
owning one leaf ceiling, one executor, one adaptive RunPool, and one credential-pool
lifecycle, whether the work is a scalar step, a fan-out item, or a composite descendant
several scopes down.

Around that, this release makes local Gemini fan-out safe to run, gives the browser and
`status` views the run’s actual runtime facts instead of authored ones, hardens GCP
Batch dispatch, and ships Metaproc’s full documentation set inside the wheel.

It also removes public CLI surface.
Read the Compatibility section before upgrading.

## What’s Changed

### Features

- **Mapped composite scopes:** a `mode: composite` step may declare `for_each` and run
  one child process scope per item, in-process, under `<run>/<step>/<item-key>/`. Each
  parent item records durable status, attempt history, validated outputs, and a result,
  and each scope binds one canonical identity to its run directory, template variables,
  task state, and child event stream, so a fixed child output path stays isolated per
  item. Scope evaluation defaults to a bounded concurrency of 32 and waits for siblings
  to finish after an ordinary item exception; cancellation terminally records the
  affected parent attempt.
  A scope is a DAG rather than a step, so one step failing blocks only that failure’s
  transitive dependents and independent branches in the same item still run.
  The first implementation is single-host: `gcp-worker` partitioning and whole-scope
  `for_each.retry` are rejected before any DAG step or cloud dispatch starts, while
  retries remain available on child leaves.

- **One execution context across recursive scopes:** local `run-process` execution
  shares one executable-leaf ceiling across fan-out pools, scalar steps, code work, and
  composite descendants, and lazily owns one adaptive RunPool that every scalar agent
  leaf submits to, so pressure response, process-tree supervision, status, and events
  are the same wherever a leaf runs.
  Synchronous handlers and code commands run on the run-owned executor rather than
  blocking the event loop, command-backed code steps at the same DAG level may now run
  concurrently, and `--force` reaches composite descendants while root step selectors
  stay root-scoped. Because commands share the process directory, authored steps that
  mutate shared files, repositories, or lockfiles must declare per-item paths or provide
  their own synchronization.

- **One credential-pool lifecycle for scalar and fan-out agents:** non-fan-out agent
  steps now lease the configured pool label, apply the same credential scope and scrub
  rules, classify failures, walk fallback labels on retry, and emit the same
  `auth_lease_acquired` and `auth_outcome` evidence as RunPool items.
  Nested leaves bind slots and event join keys to their path-relative child scope, so
  credential material stays inside the logical run tree even when a run directory is
  symlinked to another volume.
  An adapter mismatch emits an explicit warning, log record, and `auth_skipped` event
  before falling back to ambient authentication, including on worker entrypoints.

- **Views built on runtime facts:** `VizModel` now carries public process outputs, the
  complete process-input and default declarations, and the resource, failure,
  execution-profile, namespace, and fan-out fields a resolved plan carries, and the
  Metabrowser process and step panels render them.
  Given a run directory, the same model includes a rebuildable view of scalar, mapped,
  and nested task records: a result is consumable only when it names the latest
  successful attempt, matches the current step fingerprint and declared output port, and
  resolves to an available artifact of the declared kind.
  Historical unbound, stale, missing, undeclared, and external outputs remain visible as
  diagnostics, and hydrated runs rebase portable paths to the local run root without
  writing an additional ledger for the projection itself.
  Every run scope does now carry a `run-plan.yaml`; see “New and changed runtime
  artifacts” in Compatibility.

- **A refused launch reports every class of problem at once:** `run-process`,
  `run-step`, `plan`, and `deps` collect unresolved template placeholders, unset
  operator parameters, missing input files, and unusable execution profiles together and
  report them as one grouped message.
  Process-input errors are tagged as a parameter or a file, because “pass a `--var`” and
  “produce a file” are different fixes.
  Previously each launch surfaced exactly one class, so a cohort with four problems took
  four failed launches, and `--dry-run` kept passing an invocation that was wrong in
  three other ways.

- **GCP Batch dispatch:** `metaproc gcp run` stages immutable source artifacts: it
  validates artifact identity before packaging and creates wheel and workspace objects
  only when their GCS names are unused, so a later dispatch cannot replace bytes an
  existing job references.
  Re-running a dispatch that failed after uploading still works: an object with an
  identical digest is accepted as already uploaded, while one with different content
  fails by name with the instruction to pick a new `--job-name`. Batch job
  specifications now carry Secret Manager references rather than plaintext-expanded
  `secret_variables`, require an explicit runtime service account once a job binds any
  secret reference, reject registered credentials passed through `--env` or plugin
  bootstrap variables, and retry transient startup failures.
  Storage posture is explicit: the default Filestore placement is refused when
  `METAPROC_GCP_FILESTORE_SERVER` is unset, before anything is uploaded or dispatched.

- **Gemini 3.7 and 3.8 Flash:** `gemini-3.7-flash` and `gemini-3.8-flash` join the
  validated model set, with a `gemini-flash-38` execution profile beside the existing
  3.6 one. The 3.6 profile still pins `gemini-3.6-flash`, so a name that says 36 keeps
  meaning 3.6, but its lane sizing changed along with every other gemini-cli profile:
  see “Gemini lanes are sized from measured memory” in Compatibility.
  Agent CLI contracts advance to Claude Code 2.1.234, Codex 0.147.0, Gemini CLI 0.55.1,
  and Pi 0.84.2.

### Fixes

- **Gemini no longer scans its whole project history at startup.** Gemini CLI runs
  session-retention cleanup as an un-awaited background task during startup, and before
  it knows which sessions are expired it enumerates the project’s saved conversations
  and parses every one through a single unbounded `Promise.all`. On an accumulated
  project bucket that turned a roughly 0.4 GB process tree into 5 GB or more for the
  same short prompt, enough to destabilize a host running several agents at once.
  The adapter now ships `general.sessionRetention.enabled: false`, which makes cleanup
  return before it enumerates anything.
  This is a Gemini-specific guard, and the evidence for it is Gemini-specific too.
  Matched probes of Claude Code, Codex CLI, and Pi under the same conditions found no
  comparable startup cost, and stored history did not predict one: Claude Code carried
  roughly 1.5 GB of project history and Codex roughly 6.4 GB active plus 10 GB archived,
  yet neither read its full history at startup.
  No equivalent setting ships for the other adapters, because no equivalent problem has
  been measured in them.
  See Compatibility: this also disables Gemini’s own pruning of `chats/` and
  `tool-outputs/`.

- **A Gemini step is answered by the model it asked for.** gemini-cli rewrites any model
  id ending in `flash` that it does not recognize to its own default before the request
  leaves the process, and under Vertex authentication that default is
  `gemini-3.5-flash`, so a step pinned to `gemini-3.6-flash` was answered by 3.5 with no
  error, no warning, and a `stats.models` naming the substitute.
  The adapter now asserts gemini-cli’s dynamic model-resolution setting beneath its
  native-settings defaults, which passes an unrecognized id through untouched, and a
  successful result whose terminal `stats.models` omits the requested model is rejected
  for both scalar and fan-out agent steps, before valid-output rescue.
  This is upstream `google-gemini/gemini-cli#28859`, still unfixed at 0.55.1 and later.

- **A Gemini step can read files your ignore rules exclude.** The adapter now ships
  `context.fileFiltering.respectGitIgnore: false` in its Gemini native settings, so the
  agent’s own file tools read ignored files anywhere in the workspace rather than only
  declared runtime inputs.
  This makes a step see the working tree an operator sees, which is what the surrounding
  fixes assume, but it widens what a Gemini step can reach: **treat the workspace,
  including files such as `.env`, as readable by a Gemini step**, and keep material you
  do not want an agent to read out of the process directory rather than relying on an
  ignore rule. This applies to gemini-cli steps only.
  An operator who wants the previous behavior can set the key back through
  `native_settings`, at the cost of the ignored-file reads the adapter now expects.

- **A Gemini step runs where its configuration says.** `working_directory` is now an
  accepted Gemini config key and is returned to the launcher instead of `None`, so
  per-run isolation is real rather than an inherited repository root.
  Gemini prompts are also streamed through stdin while the durable audit prompt is
  retained, so a workspace ignore rule can no longer block or distort prompt delivery.

- **An agent’s own verdict outranks its exit code.** Some adapters write every declared
  output, emit a terminal success record, and then exit nonzero while shutting down.
  A scalar agent step whose agent reported success and whose declared outputs all
  validate now completes, and the exit code is retained as an accepted anomaly —
  attempt-owned, versioned evidence rather than a discarded fact.
  The override is narrow: never a step with no declared outputs, never an agent that did
  not claim success, and never a process the supervising RunPool killed.
  Startup banners are no longer mistaken for failure causes either: a terminal `result`
  record is consulted before the last-non-JSON-line fallback, and that fallback
  considers only lines written after the last structured record.

- **Agent transcripts are free of terminal styling.** All four agent launch paths, and
  the probe paths that launch an adapter CLI and parse its output, seed the child
  environment with `NO_COLOR`, `FORCE_COLOR=0`, `CLICOLOR`/`CLICOLOR_FORCE` off, and
  `TERM=dumb`. ANSI sequences in a JSONL transcript had no reader and were corrupting
  failure classification and tool-use probes.
  A step’s authored `env` block is still applied afterward, so an explicit override
  remains possible.

- **A raw path an upstream step writes is execution state, not authored input.**
  `produced_refs` now covers a raw `prompt_paths` or `uses` entry whose exact path a
  step this one depends on declares as an output, so its bytes leave the step
  fingerprint the way a dep-ref’s already did.
  Only transitive dependency ancestors count: a step declaring the same output path
  while running independently or downstream supplies nothing to the reader, and a path
  two upstream steps both declare is refused at plan time rather than resolved
  arbitrarily. Before, a real authored input could go stale without invalidating
  anything, or a run could fail on a file the plan had promised.

- **Terminal paths retain owned capacity until cleanup finishes.** On completion,
  timeout, or cancellation, agent and code-command process groups are terminated,
  stubborn descendants are killed, and log filters are flushed before run slots or host
  admission are released; late credential leases are torn down before credential
  capacity is released.
  Cleanup after an exited leader is fenced by process identity, and cleanup failures are
  reported without replacing the command result or cancelling the remaining shutdown
  work. Ctrl-C follows cooperative asyncio cancellation and SIGTERM retains the hard
  descendant reaper, and a hard process-tree reap also remains at the outermost CLI
  boundary on the Ctrl-C path, because a second Ctrl-C can raise before cooperative
  cleanup finishes. Forced RunPool shutdown gives cancelled futures a terminal attempt
  and credential outcome and drains queued and late-launching submissions, bounded so
  final status, events, health state, and log closure still run if backend cleanup
  wedges. Long-running Python handlers can observe the request through
  `StepContext.cancel_requested()`.

- **Status tells the truth about a run in progress.** `run-process` fan-outs have no
  `progress.md`, so `status` had been treating the tasks observed so far as the total
  and reporting `pending` as zero mid-dispatch; it now reads the per-step item roster
  from the recorded run plan.
  `status` and `pool status` reject a nonexistent local run directory instead of
  projecting an empty tree as complete, and a resumed run writes a fresh process
  projection when recursive evaluation begins, so `status`, `wait`, and completion
  checks no longer report a prior failure or cancellation as terminal while an
  orchestrator still owns the run.

- **A bare resume no longer re-invokes completed code fan-out items.** A `mode: code`
  step with `for_each` that is not part of an item-aligned chain received every
  non-terminal item from discovery, completed ones included, and invoked all of them.
  Resuming such a step under the same `RUN_ID` re-ran every handler that had already
  succeeded and recorded a fresh attempt for each, and an item already running under a
  live sibling could be invoked concurrently.
  The step now reuses an item whose task record is `completed` or `cached` and whose
  declared output still validates: the same guard the aligned-chain executor already
  applied per item, now shared by both paths as one implementation.
  Reuse is earned by a valid artifact rather than by a status file alone, so an item
  whose output has since been removed still reruns, and `--force` is unaffected.
  This also bounds what a completed scalar composite costs when it is re-entered on
  resume, since a child containing such a step was the case where re-entry did real work
  rather than reloading state.

- **Launch-refusal classes beyond the two most common.** Alongside unresolved
  placeholders and process-input failures, a launch is now also refused for an unusable
  execution profile, an unknown adapter override, and a raw path that two upstream steps
  both declare as an output.
  All of them refuse before any step runs and exit 2. The multi-producer rejection is
  new in this release, so a spec that planned on v0.3.0 and relies on an ambiguous
  producer now fails at plan time and must name one owner.

- **Plan-time correctness:** static validation resolves declared process-input defaults
  instead of reporting false missing-input failures; item discovery rejects two source
  rows resolving to the same `for_each.key` before either can write the shared task,
  log, output, or child-scope namespace; and a step’s referenced files are no longer
  required to exist before the run that produces them starts.

- **Fan-in failure propagation across dependency diamonds.** `require: finished`
  tolerates failure only for affected direct dependencies collected with that policy.
  A separate success-requiring path from the same failure still blocks the consumer, and
  an unaffected required dependency does not erase the tolerant collection.

- **Resume rejects changed resolved inputs.** An existing run compares the persisted
  resolved-variable mapping against the new launch before reusing task state.
  Only known equivalent Filestore aliases for `RUNS_DIR` normalize across local and
  cloud topology, and mismatch errors list field names without exposing their values.

- **Cloud authentication policy no longer half-arrives.** `run-process --cloud` carries
  the complete authentication-pool configuration as one typed value through orchestrator
  dispatch, so selection policy could no longer be silently dropped while neighboring
  authentication flags reached the cloud job.
  A mounted Filestore preserves attached-identity ADC precedence on persistent GCP
  hosts, full-cloud dispatch supplies its own `METAPROC_GCP_ORCHESTRATOR` admission
  marker rather than depending only on `BATCH_TASK_INDEX`, and `gcp run` passes its
  required `METAPROC_GCP_PROJECT` through wheel and workspace uploads so service-account
  ADC without an embedded project ID can dispatch.
  A credential teardown exception records the affected attempt as lost before
  propagating the operational error.

- **A fail-fast stop no longer names a flag nobody passed.** A step failure reported
  `Step '<id>' failed (--no-continue-on-error set)` unconditionally, including when the
  policy came from a default.
  The message states the policy in force rather than asserting how it was set, and names
  `continue-on-step-failure` as well when a scope is what stopped.

### Documentation

- **The core documentation set ships in the wheel.** `metaproc help` serves 17 topics
  instead of 3, covering the design doc, the conventions, the artifact catalog, the
  general framework model, the credential and cloud-dispatch runbooks, and all seven
  architecture documents, so a consumer reading from an installed wheel has the same
  documentation as a reader of the repository.
  `metaproc help` with no topic lists them in reading order with approximate sizes, and
  the Agent Skill catalog lists the full set.
- Documentation paths moved: `docs/arch/` is gone, its contents now in
  `src/metaproc/docs/`; `arch-metaproc-core.md` is `metaproc-design.md`;
  `docs/releases/` is `docs/project/releases/`. Two shipped documents were also renamed
  inside the package: `metaproc-concepts-and-principles.md` is `metaproc-concepts.md`,
  and `docs/process-framework-concepts.md` is now
  `src/metaproc/docs/process-framework-theory.md`. The `concepts` help topic name is
  unchanged, but a reference to the old packaged filename, including one resolved
  through `importlib.resources`, needs updating.
  Project-internal material moved under `docs/project/design/`.

## Compatibility

- **Removed public CLI surface.** `gcp remote`, `gcp remote-run`, `gcp self-install`,
  `gcp archive`, `status --cloud-runs-dir`, `status --remote`,
  `validate --cloud-runs-dir`, and `pool retry-missing` are gone, along with the
  `METAPROC_GATEWAY_HOST` and `METAPROC_GCP_FILESTORE_REMOTE_RUNS_DIR` environment
  variables. No CLI command or flag was added in this release.
  Batch-native status and logs remain; filesystem-oriented commands now require an
  explicit locally visible run directory; hydrated and full-cloud runs use one run tree
  for state, output validation, and recovery; and consumers own durable run publication
  and retention.

- **`status --remote` is gone, and so is remote auto-detection.** The flag forced
  resolution on the gateway VM over IAP SSH, and a bare `metaproc status <run-id>` used
  to auto-detect a run id and resolve it remotely.
  Both are removed with the rest of the gateway surface: `status` now takes a locally
  visible run directory and rejects anything else.
  A script running `metaproc status "$RUN_ID" --remote`, or relying on the bare run-id
  form, must pass a real path.
  Batch-native `gcp status` and `gcp logs` remain.

- **`status --check` can now fail a run whose items all completed.** The check consults
  the process-level record first, so a run recorded as failed or cancelled exits 1 even
  when every per-item task reached `completed`; previously it exited 0. `status` text
  output gains `FAILED` and `CANCELLED` labels and a `Failure:` line, and
  `status --json` gains `process_execution_state` and `process_error`. A CI gate on
  `status --check` may start failing runs it used to pass; that is the intended
  correction, but it is a behavior change to schedule for.

- **Workstation-mounted Filestore aliases are no longer resume identities.** Resume
  normalization now anchors a known Filestore alias at the start of the path instead of
  matching it anywhere inside.
  A run under a workstation mount such as `<workstation-mount>/filestore/runs/<id>` used
  to normalize to the canonical cloud path and resume; it now fails with an explicit
  mismatch error. Resume from the canonical path instead.

- **`metaproc gcp run --job-name` rejects values it used to accept.** The name must be a
  lowercase GCP-safe id: at most 63 characters, beginning with a letter, and unchanged
  by label sanitization.
  Uppercase, underscores, and a leading digit now fail at parse time.

- **`gcp run` pins uv to the baked image environment for no-workspace runs.** A run
  without an extracted workspace now sets `UV_PROJECT_ENVIRONMENT=/opt/venv` and
  `UV_NO_SYNC=1` before handing off, matching what a workspace run already did.
  A step command that shells out to `uv run` and expects project resolution or an
  implicit sync gets the baked environment and no sync instead.

- **The Pi adapter’s npm package moved scope.** Install
  `@earendil-works/pi-coding-agent@0.84.2`; the previous `@mariozechner/pi-coding-agent`
  name is not the package this release pins.
  An image build or install script that copies the old line resolves a stale package and
  then fails the adapter version check.

- **The `batch_backend` secret API is removed.** `GCP_SECRET_REFS`,
  `resolve_gcp_secret_ref`, `_build_secret_env_vars`, and the
  `GCPBatchConfig.secret_env_vars` field are gone; `create_single_task_job` takes
  `secret_refs`, and `SecretRefSet.to_secret_variables` is now `resolve_env_refs` with
  no `as_tuples`. Constructing `GCPBatchConfig(secret_env_vars=...)` raises `TypeError`.
  This breaks direct Python callers only; the CLI surface is unchanged.

- **New and changed runtime artifacts.** Consumers that read the run tree or pin schema
  tokens have several changes to absorb: every run scope now writes
  `<scope>/.state/run-plan.yaml` (`metaproc:RunPlanSnapshot/0.1`); accepted-anomaly
  evidence is `accepted-anomalies.yaml` under the attempt directory
  (`metaproc:TaskAttemptAnomalies/0.1`); task output projections carry
  `metaproc:TaskOutputProjection/0.1`; and `result.yaml` gains an optional `attempt_id`.
  Four existing tokens moved: `metaproc:VizModel/0.2` is now `/0.4`,
  `metaproc:StepDetails/0.1` and `metaproc:ProcessHeader/0.1` are now `/0.2`, and the
  resource snapshot is `metaproc.resource-snapshot/v2` with v1 still readable.
  A reader that dispatches on an exact token needs updating; `metaproc help artifacts`
  carries the full catalog.

- **`METAPROC_GCP_SECRET_REFS_JSON` is a new dispatcher-owned variable**, carrying the
  reference-only secret contract into the container.
  Passing it through `gcp run --env` is refused like the other reserved keys, and names
  listed in it are redacted from the startup resource dump.

- **Smaller surface changes worth knowing.** `pool rollup` reports the run-owned pool as
  an extra entry keyed `.` alongside per-step pools.
  A third-party `TraceExtractor` registered by entry point should declare
  `scope_local = True` to be invoked inside composite child scopes; without it, it keeps
  once-per-parent behavior silently.
  The Gemini adapter now launches its CLI through `/bin/sh -c` to stream the prompt on
  stdin, so `/bin/sh` is required in the execution environment and the child argv
  differs from the bare `gemini` form.
  `check-handlers` and `check-headers` now expand process variables when resolving
  dependency paths, so a spec that reported a false failure from either command passes.
  GCS artifact uploads use 16 MiB chunks with a 120-second per-request timeout and a
  10-minute retry deadline, which lets a large workspace finish on a slow uplink and
  makes a genuinely stuck upload take longer to surface.
  Agent fan-out progress can report `status=result_contract_failed` for a result
  rejected by the terminal-contract check.
  The `httpx2` dev dependency was dropped; it never shipped in the wheel.

- **Full-cloud GCP topology is enforced.** `run-process --backend gcp-worker` from an
  operator host fails unless `--cloud` is also set, and direct non-dry
  `run-parallel --backend gcp-worker` execution requires the GCP Batch runtime marker.
  The bare backend form remains available to the inner Batch orchestrator, and dry runs
  remain available for inspection.

- **GCP runs require an explicit storage posture.** `metaproc gcp run` refuses its
  default Filestore placement when `METAPROC_GCP_FILESTORE_SERVER` is unset; a caller
  that wants ephemeral task storage must pass `--no-filestore`.

- **Roll out the hydration-capable agent image before its dispatcher.** Batch job
  specifications now carry Secret Manager references rather than plaintext-expanded
  values, and a stale image cannot interpret the reference-only contract.

- **A refused launch exits 2.** `run-process` and `run-step` exit 2 when a launch is
  refused before any step runs: unresolved placeholders or failed process-input
  validation. This matches the documented validation exit code `plan` and `deps` already
  used for the same checks.
  A completed run still exits 0 and a step failure still exits 1. A retry script that
  treated any nonzero exit as a run failure will now see 2 for an invocation that never
  started.

- **A failing scope spends more, not less.** A scope now continues past a step failure
  exactly as the root does, so the independent branches it used to abandon will run —
  real provider cost in a scope with agent-bearing steps.
  Steps that previously stayed `pending` after a sibling’s failure are now `completed`
  or `blocked`. Only the default pair (`continue_on_error=True`,
  `continue_on_step_failure=False`) changes behavior; `--no-continue-on-error` still
  fails the root fast.

- **Composite output declarations are enforced.** Scalar and mapped composites validate
  every declared child-process output before completing, and resume revalidates those
  child outputs even when the mapped parent publishes only a subset.
  Existing composite specs with inaccurate output declarations must correct or remove
  them.

- **Agent CLI adapter modules were renamed** to `claude_cli.py`, `codex_cli.py`,
  `gemini_cli.py`, and `pi_cli.py`. Adapter type strings and adapter class names are
  unchanged, so this breaks only a direct module import.

- **Gemini `native_settings` merges rather than replaces**, so a profile-supplied block
  cannot silently drop a host-safety default it never mentions, and
  `native_settings: null` no longer suppresses injection entirely: the retention guard
  is re-asserted beneath the defaults.
  An operator who deliberately sets a key still wins.
  Because disabling session retention also disables Gemini’s `cleanupToolOutputFiles`,
  Gemini no longer prunes its own `chats/` and `tool-outputs/` directories: **bounded
  retention becomes an external operation**, and those directories grow until something
  else trims them.

- **The Gemini adapter rejects `no_session_persistence`.** The key was in the allow-list
  but never read, so a spec could ask for session isolation and silently not get it.
  Gemini CLI has no headless flag that disables session recording, so the key is now
  refused with an explanation.
  No built-in Gemini profile set it.
  The equivalent no-op in the Pi adapter is tracked separately and unchanged.

- **Gemini lanes are sized from measured memory.** The three gemini-cli profiles
  (`gemini-flash-36`, `gemini-flash`, `gemini-pro`) estimate 250 MB per process with a
  0.5 initial memory budget fraction, replacing the 500 MB and 0.25 clean-state figures;
  a Gemini process measures 113 MB mean across a run tree and 187 MB on its own once
  session retention is off.
  Claude profiles are unchanged, and so are `pi-gemini-flash` and `pi-gemini-pro`: they
  reach Gemini models through `pi-cli`, which the retention guard does not touch, so
  they keep the 500 MB and 0.25 figures.
  Expect more concurrent lanes on the three gemini-cli profiles and no change on the
  `pi-cli` ones.

- **Authentication event `run_id` is a run-tree path scope**, not a root-only
  identifier: composite fan-out slot paths and authentication-event `run_id` values now
  include the child scope.
  Consumers reading those events should treat the field accordingly.

- **`softschema>=0.8.0,<0.9` is required.** Structural failures map to SoftSchema’s
  stable error `code` rather than a JSON Schema engine keyword, and property-level
  failures resolve to the affected field in Metaproc’s existing `location` value.
  Supported composed and conditional schemas can therefore use `status: enforced`
  without a Metaproc-specific schema layer.
  `metaproc softschema repair` is unaffected and keeps routing through Metaproc’s own
  YAML repair.

- **The optional `browser` extra requires `metabrowser==0.9.1` and browser plugin SDK
  0.5.** Plugin discovery refuses a manifest declaring the wrong SDK, so the dependency
  and the bundled plugin move together; a downstream plugin built against SDK 0.1 must
  migrate with them. Metaproc’s own views, kinds, data hooks, and sidekick routes are
  unchanged, and the unconsumed `MetaprocDomainViews.openPath` re-export is gone.

- **Attempt records stay readable by v0.3.0.** The strict
  `metaproc:TaskAttemptRecord/0.1` payload is unchanged; accepted-anomaly evidence lives
  in a separately versioned, attempt-owned sidecar with an in-memory `anomalies`
  projection, so a v0.4.0 run remains readable if you roll back.

- **Replay parity keeps one known gap.** A task blocked purely on credential-pool
  capacity is recorded as running with a persisted attempt before admission is granted,
  and replay counts those lost records against `max_attempts`, so a run that merely
  waited on capacity can replay as failed while production considered it healthy.
  Live execution is unaffected.
  Tracked as `mp-ux0f` and `mp-f5m5`.

- **A completed scalar composite is re-entered on a bare resume.** A `mode: composite`
  step with no `for_each` writes no per-task status record, so the resume completion
  check falls through to the process-status projection, which the orchestrator has
  already reset to `pending` for every active step.
  The child scope is therefore reparsed, replanned, revalidated, and given a fresh
  `process_start` on each resume of the same `RUN_ID`. Child leaves still skip from
  their own durable records, so no handler runs, no agent launches, and nothing is
  charged to a provider: the cost is structural work and an event log that gains a start
  record per resume. `--force` and a first run are unaffected.
  The fix depends on settling what an attempt means for a step whose work is a whole
  child DAG, which is a design question rather than a patch, so it is deliberately not
  in this release. Tracked as `mp-ad60` for the defect and `mp-5nko` for the question.

- **Legacy run trees remain readable**, with readers falling back to status-based
  compatibility when durable task facts are absent.
  The full mixed-authority boundary is still being proven out under `mp-g315`.
