Three commands report success after a batch in which targets failed.

1. **`commands/gcp.py:1408-1426`** — the cancel loop catches `Exception` per job, prints
   `Failed to cancel <job>: <exc>`, then prints `Cancelled {cancelled}/{len(running_jobs)}
   jobs`, writes the kill sentinel, and **returns exit code 0** even when
   `cancelled < len(running_jobs)`. Automation wrapping `metaproc gcp cancel` proceeds
   believing every job is stopped. `commands/gzip_text.py:559-560` has the right shape —
   `raise typer.Exit(code=1)` when any file failed.

2. **`commands/pool.py:1406-1407`** — `if override_path.exists(): override_path.unlink()`
   inside a loop over many candidate paths. A pool process removing its own override
   between the two calls raises `FileNotFoundError` out of the loop, so the remaining
   overrides are never cleared *and* the "Removed N override file(s)" summary never
   prints. The operator is told nothing and believes the clear failed entirely. Fix:
   `unlink(missing_ok=True)`, counting only actual removals.

3. **`cloud/gcp/dispatch_artifacts.py:251-253`** — `package_workspace` logs a warning for
   a path absent from the working tree and ships the tarball anyway. This is documented
   and `required_paths` does raise, so the narrowing is deliberate — but the default
   git-scan path can silently ship an incomplete workspace when the tree changes under
   the scan, and the final `log.info` reports `len(paths)` rather than the number actually
   emitted. At minimum report the skipped count.

`filesystem-rules`: "An exit code of zero after a batch in which three of ten targets
failed is a bug in the same class as data loss: the caller's automation proceeds on a
false premise."
