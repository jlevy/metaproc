Three state files are mutated read-modify-write with no serialization. Each individual
write is atomic, so no file is ever corrupt — the failure mode is a silent lost update.

1. **`io/dispatch_manifest.py:77-100`** — `append_dispatch_manifest` reads, merges, and
   republishes with no lock. Two overlapping dispatches lose worker entries, and a resume
   then re-dispatches workers it believes were never submitted. This is the one that
   matters. The module already has `io/mkdir_lock.py` available as a sibling; note that
   `mkdir_lock`'s own reclaim race (mp-xhr6) should be fixed first or this inherits it.

2. **`commands/run_process.py:1263-1268`** — a resume adopting `step_variants` reads
   `run-config.yaml` at 1263 and republishes it at 1267. Two concurrent resumes lose one
   update. In practice the orchestrator lease makes concurrent resumes unlikely, which is
   why this is listed rather than blocking.

3. **`io/overrides.py:179-249`** — `upsert_override` / `clear_override`. Operator-driven
   CLI, low concurrency. Note only.

Also in `io/claimed_items.py:136-140`: `clear_claimed_items` unlinks the registry
**outside** the lock every other mutation holds. `claim_item` holds `_step_claim_lock`
and calls `collect_claimed_items` → `read_claimed_items`, which does `path.exists()` then
`read_yaml_file(path)` (`:44-48`). An unlocked `clear_claimed_items` landing between
those two lines raises `FileNotFoundError` out of the claim path. Fix: take
`_step_claim_lock` and use `unlink(missing_ok=True)`; belt and braces, catch
`FileNotFoundError` around the read so a vanished registry reads as "no claims".
